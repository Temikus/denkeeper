## Architecture

Denkeeper is a single-binary personal AI agent with multi-agent routing:

```
Adapter (Telegram/Discord) ─┐
Web Dashboard (WS/SSE) ─────┼→ Dispatcher → Engine (per agent) → LLM Router → Provider (Anthropic/OpenRouter/OpenAI/Ollama)
REST API (/api/v1/chat) ────┘                    ↕                    ↕
                                             MemoryStore          CostTracker
                                             (SQLite)              + Pricing Registry
```

- **Dispatcher** (`internal/agent/dispatcher.go`): routes messages to Engines via channel bindings (or legacy adapter bindings), falling back to the `"default"` agent. Sends inline-keyboard approval messages for `tool_approval` ChatEvents; intercepts `/session` for runtime channel switching.
- **Channels** (`internal/agent/channel.go`): named routing endpoints decoupling sessions from 1:1 agent–adapter binding. A channel points to one agent, can bind multiple adapters (cross-adapter session sharing). Config `[[channels]]` (`name`, `agent`, `adapters`); auto-synthesized from agent `adapters` when absent. Conversation ID `"chan:{name}"`. `/session <name>` switches; selections persist in SQLite `active_channels`.
- **Engine** (`internal/agent/engine.go`): per-agent orchestrator. Pipeline: permissions → get/create conversation → store user msg → load history → system prompt (persona + skills) → `Router.Complete()` → tool-call loop (with approval if supervised) → usage event → memory extraction → store assistant msg → return.
- **Three key interfaces**: `adapter.Adapter` (platforms), `llm.Provider` (LLM backends), `agent.MemoryStore` (SQLite persistence).
- **Multi-agent config**: `[[agents]]` with `name`, `persona_dir`, `adapters`, `llm_provider` (overrides global `default_provider`), `llm_model`, `session_tier`. With no `[[agents]]`, a single `"default"` agent is synthesized when an adapter token is set (headless, bound to those adapters) **or** `api.enabled` is explicitly true (API-only, no bindings). Nothing configured → no agent, so the web setup wizard can guide creation; synthesis runs before `api.enabled` defaults to true so "explicit" is distinguishable.
- **Named provider instances**: `[[llm.providers]]` allows multiple instances of one provider type (`name`, `type`, `api_key`, `base_url`, `organization`). Legacy `[llm.openai]` single-slot syntax auto-converts. Per-agent `llm_provider` references by name.
- **Data directory**: all default paths (db/persona/skills) derive from one base dir — `DENKEEPER_DATA_DIR` env > `data_dir` TOML > `~/.denkeeper`. Helm sets `DENKEEPER_DATA_DIR=/data`.
- **Wiring** is in `cmd/denkeeper/main.go`; all behavior should be TOML-configurable, not hardcoded.

## Conventions

- **Error wrapping**: always `fmt.Errorf("context: %w", err)`.
- **Logging**: `log/slog` with contextual fields.
- **Context**: all I/O functions accept `context.Context`.
- **Concurrency**: channels for message passing; `sync.Mutex` for shared state.
- **Config**: three-phase — parse TOML → apply defaults (incl. env) → validate. `applyEnvOverrides()` reads an explicit allowlist of `DENKEEPER_*` vars.
- **Cyclomatic complexity**: gocyclo threshold 15 for all non-test functions.

## Testing Patterns

- **Coverage thresholds are quality gates** — never lower to make CI pass; add tests instead. Only the project owner may approve lowering one.
- Hand-written mocks (no codegen); in-memory SQLite via `NewInMemoryStore()`; individual `TestName_Scenario` functions (not table-driven); always `-race`.
- Web UI must be built before Go steps that embed `internal/web/dist/` (`ensure-web-dist` recipe handles it; CI uses an explicit `build-ui` job).
- **Web UI**: Vitest + jsdom + MSW; tests in `web/src/__tests__/` and `web/src/components/__tests__/`.
- **E2E** (`internal/integration/`): full in-process API server, mock LLM, in-memory stores via `NewHarness(t, &HarnessOpts{...})` (`ConfigPath`, `WithLifecycleMgr`, `Responses`). WebSocket tests need `httptest.NewServer`; the rest use `httptest.NewRecorder`.

## Permission Tiers & Approval Workflows

Tiers: `autonomous` (all actions), `supervised` (chat + tools with approval), `restricted` (chat + read-only tools).

`internal/approval/` manages human sign-off. Flow: Engine submits → Manager persists + registers closure → inline Approve/Deny keyboard → callback resolves → closure invoked. Eleven action kinds: `user_update`, `soul_update`, `identity_update`, `create_skill`, `update_skill`, `delete_skill`, `modify_schedule`, `install_tool`, `modify_config`, `browser_profile`, `tool_call`.

**Supervised tool calls**: each MCP call needs approval. Engine checks `Manager.ShouldAutoApprove()` first (match → immediate execution, `tool_approval` event with `auto_approved`), else blocks on `WaitForResolution`. Dispatcher sends four buttons: Approve, Deny, Auto (session), Auto (always). Denied calls feed "Tool call was denied by the operator." to the LLM. Within one turn, a name+args exact match against an already-denied call is auto-denied (status `auto_denied`); dedup map resets on next user message.

**Auto-approve rules**: three scopes, checked `config` → `session` → `permanent`. `session` (in-memory, conversation-scoped, 15m TTL) and `permanent` (SQLite, agent-scoped) are created at runtime from Telegram buttons (`:approve_session`/`:approve_always`), web UI Always Approve, or REST; `approval.ExtractToolName()` keys them from the approval summary. `config` is declared per agent in TOML (`[[agents]] auto_approve_tools = [...]`), held in memory on the Manager, and **replaced wholesale** by `SetConfigRules` — the only writer, called from the config-load path (startup + `POST /server/reload`). It cannot be weakened at runtime: `POST /auto-approve` 400s on `scope: "config"`, config rules are listed with an empty `id` so DELETE has nothing to address, and `RemoveAutoApproveRule`/`ClearSessionRules` touch different state. Ordering cannot change an approve/deny outcome (all three answer the same question) — it fixes **attribution** (`scope=config` stays stable across sessions) and skips the SQLite lookup for the hottest calls. Newly-blessed pairs auto-resolve queued approvals, same as the other two scopes. Validation is syntax-only at load (non-empty, no whitespace, unique — `ValidResourceName` deliberately not applied, MCP names have hyphens); names not matching an advertised tool are **warned about at wiring/reload and kept**, never dropped (a late-connecting remote server must not silently weaken policy). Stage-1 auto-approvals emit an `audit.CategoryApproval` / `auto_approve` event with `detail.scope` for **all** scopes.

**Supervisor agents**: `supervisor = "agent-name"` on a supervised agent inserts an LLM reviewer between auto-approve and human approval: APPROVE / DENY (reason fed to LLM) / ESCALATE (→ human). One-shot LLM call via the supervisor's Router with tool details + recent history — no storage/skills/tool loops. Emits `audit.CategorySupervisor` events and `tool_approval` statuses `supervisor_approved`/`_denied`/`_escalated`/`_error` (error falls through to human). Web UI: supervisor controls in Agents, statuses in Chat, filter chip in AuditLog.

## Cost Tracking & Pricing

`internal/llm/pricing/` — registry with bundled defaults for ~70 models. `TokenCost(resp, reg)` returns `(cost, source)`; source becomes the `pricing_source` OTel attribute. Unknown models log a warning. `TokenUsage.CachedPrompt` from Anthropic `cache_read_input_tokens` / OpenAI `prompt_tokens_details.cached_tokens`.

Config: `[costs] default_rate_per_1k_tokens` (fallback when model unknown; 0 = $0 + warn); `[costs.model_prices.<model>]` with `input`/`output`/`cached_input` in $ per million tokens (`cached_input` 0 = same as input).

## MCP Tools & Health Monitoring

`internal/tool/manager.go` manages MCP servers (stdio subprocess or SSE remote).

- **Health**: `StartHealthChecker` probes via ListTools every 30s; crashed servers auto-restart with backoff. `[mcp]`: `auto_restart` (true), `max_restart_attempts` (3), `restart_cooldown` ("5m"), `drain_timeout` ("35s"). `ServerStatus`: `connected`/`connecting`/`draining`/`error`/`disabled`/`config_error`/`pending_auth` + restart_count/last_error/uptime. Manual restart & enable/disable via Manager/LifecycleManager, REST, or Config MCP.
- **Two-phase teardown (drain before close)**: `UnregisterServer` is the single funnel for remove/disable/enable/restart/update *and* health-checker auto-restart, so all of them inherit drain behaviour with no per-path code. Phase 1 (write lock, fast) unpublishes: `serverConn.beginDrain()` flips `drainStateLive`→`Draining`, then the server leaves `servers`/`discoveryOrder` and `sc.tools` is cleared so `rebuildToolIndex` drops it from the advertised projection — new rounds stop seeing it and new calls are refused with the `ErrServerDraining` sentinel. Phase 2 (**no manager lock**) waits for the in-flight counter to reach zero, bounded by `drain_timeout`, then closes. Holding `m.mu` across the close is what the split exists to prevent: the MCP SDK's `ClientSession.Close` blocks until outgoing calls retire (`jsonrpc2.inFlightState.idle()` requires an empty `outgoingCalls`), so one slow teardown used to freeze every agent's `Execute`, `ToolDefs`, `ServerInfo` and the health checker for ~40s. Phase 2 stays **synchronous** inside `UnregisterServer` because `RestartServer`/`UpdateTool`/`EnableTool` re-register the same name straight after — the one exception is the SSE re-register overwrite, where a new session is already live so the replaced one drains in a goroutine. In-flight accounting (`inFlight`, `drainDone`) lives on `serverConn` under its own `drainMu`, **not** `Manager.mu`, since `Execute` must admit a call holding only `RLock`; lock order is always `m.mu` → `drainMu`. `Close()` (shutdown) runs phase 1 for every server under one lock — clearing each `sc.tools` and rebuilding, never hand-resetting a subset of the derived maps — then drains concurrently under a 5s ceiling. An expired window forces the close and emits the only new audit surface: `audit.CategoryMCP` / `forced_close` with the remaining count. The health checker skips `drainStateDraining` conns but deliberately **not** `drainStateClosed` ones — `handleServerFailure` re-inserts a closed conn when re-registration fails and relies on the next probe failing to retry. Model: the drain-before-withdraw teardown in "A Programming Paradigm for Spatiotemporal Composability" (Shi, Zhang, Cui — https://github.com/cordiverse/paper/blob/main/paper.pdf).
- **`Execute` and `ServerInfo` resolve entirely under one lock**: `Execute` takes its drain admission (`enterCall`) inside the same `RLock` that resolves the server and snapshots `session`/`disabled` — an admission decided after the unlock could let a call slip past a teardown that has already flipped the conn to draining. `ServerInfo` holds `RLock` across the whole build, not just the lookup: every field `buildServerStatus` reads (`lastError`, `restartCount`, `connectedAt`, `disabledSet`) is written under the write lock by `handleServerFailure`/`SetDisabledTools`, so building after unlocking races them on the dashboard-polled `GET /api/v1/tools` path.
- **OAuth 2.1** (`internal/tool/oauth/`): MCP OAuth for remote SSE servers — per-tool `auth = "oauth"` (+ optional `client_id`/`client_secret`/`scopes`), routes at `/api/v1/tools/{name}/oauth/...`, tokens in SQLite, `api.external_url` for callbacks.
- **Tool-name collisions** (`internal/tool/toolindex.go`): two servers may advertise the same tool name. `toolMap`/`owners`/`localOf`/`toolDefs` are **one derived projection** of each `serverConn.tools`, rebuilt wholesale by `rebuildToolIndex` on every registration change (never patched in place — in-place filtering is what used to strand or delete the *other* collider's entry in `UnregisterServer`; `UnregisterServer` therefore also clears `sc.tools`, since `handleServerFailure` re-inserts the same `serverConn`). Unique names are advertised and routed exactly as before (byte-identical `ToolDefs()`, the back-compat contract). Under collision **neither** owner keeps the bare name: each is advertised as `<server>__<tool>` (double underscore — `:` is rejected by OpenAI/Anthropic function-name charsets), and the bare name becomes unroutable, returning the `ErrAmbiguousTool` sentinel that names both servers and the qualified alternatives — never a guess. All lookups (`Execute`, `ToolServer`, `IsIdempotent`, the `enabledToolDefs` disabled check) go through `resolveTool`, which returns owner + **server-local** name: the local name is what goes on the wire and what `disabledSet`/`idempotent_tools`/`readOnlyHinted` are keyed by, while spans/metrics/errors keep the advertised name the model used. A qualified name stays resolvable after the collision clears (matched by exact server-name prefix, never by splitting on `__`), so a rule or in-flight call written against it keeps working. Only a genuine miss delegates to the parent manager; ambiguity does not. Collisions log Warn + emit one `audit.CategoryMCP` / `tool_name_collision` event (source `tool_manager`) when an `Auditor` is wired; clearing one logs Info. Auto-approve rules need no schema change — they match whatever is advertised, so a rule naming a now-colliding bare name goes inert (fail-closed, never transferred to the other server) and `warnUnadvertisedAutoApprove` says so at wiring time; `requires.tools` inherits the same rule whenever B2 starts enforcing it. `ServerStatus.ToolNames` stays **local** names (that is what the disable controls are keyed by). Origin: a review of this codebase against the composability model in "A Programming Paradigm for Spatiotemporal Composability" (Shi, Zhang, Cui — https://github.com/cordiverse/paper/blob/main/paper.pdf); the qualification scheme is the fix for a gap that review surfaced, not something the paper prescribes.
- **Security**: SSRF protection, header injection prevention, env var denylist, URL/arg redaction in API responses.
- **Stdio env scoping** (`internal/tool/env.go`, `buildStdioEnv`): children do NOT inherit the parent env (would leak `DENKEEPER_*` secrets). They get a built-in non-secret allowlist (`PATH`, `HOME`, `TMPDIR`, `USER`, `LOGNAME`, `SHELL`, `LANG`, `LC_*`, `TZ`, `TERM`; `NODE_PATH`/`NODE_OPTIONS`/`PYTHONPATH`/`VIRTUAL_ENV`/`GOPATH`; Windows equivalents) plus the tool's own `env` (appended last, wins). `env_passthrough = [...]` on `[mcp]` and/or `[tools.*]` forwards extras. A hard exclusion filter (`isExcludedEnvVar`: any `DENKEEPER_*` or the `forbiddenEnvPatterns` denylist) applies to every forwarded name — allowlist AND passthrough — so secrets can never reach the child (blocked passthroughs are logged and dropped). Only spawn site: `registerStdio`.

## Non-obvious Defaults & Invariants

Things you can't infer by reading the code at a glance:

- **TOML config writer** (`config.AddX/UpdateX/RemoveX`): atomic read-modify-write under a file mutex, `.bak` backup before each save. Comments/formatting are NOT preserved — everything round-trips through the parser.
- **Engine knobs** (all re-applied to live engines on hot-reload via `buildReloadFunc`): `SetMaxContextMessages` (50), `SetApprovalConfig`, `SetSupervisorConfig` (30s / 5 messages), `SetMaxToolRounds` (50 — counts **rounds**, not calls; a round may fan out to many parallel calls). The loop appends `[engine: N of M tool-call rounds remaining this turn]` (`toolBudgetHint`) to the **final** tool result of each round so the model reads its budget — skills should not tell the model to self-count tool calls. Stalled SSE streams capped by `IdleTimeoutReader`.
- **Per-skill `max_tool_rounds`** (skill frontmatter, same name/unit as the agent knob): the *effective* budget is resolved once per turn in `chatWithApproval` (`Engine.resolveToolBudget` → `turnToolBudget{maxRounds, skillName}`, threaded through `runLLMWithTools`/`executeToolRounds`/`runToolLoop`/`runRoundToolCalls`), so skill edits apply on the next turn with **no** hot-reload plumbing. It caps **only downward** — `min(skill, engine)`, since a skill is agent-authorable and must not raise an operator ceiling — and applies only when a *single skill explicitly drives* the turn (`drivingSkill`): `msg.SkillName` present in the matched set (schedule), else exactly one matched skill with `ParsedTriggers` (command). A lone **ambient** match deliberately does **not** cap — the divergence from `attributeSkill`, which is observational; an ambient skill matches every message, so its cap would throttle unrelated chat turns. Zero or 2+ command matches → engine cap. `stopMaxRounds` is **reused** (no new stop reason), so the wrap-up round, honesty marker, and audit statuses are unchanged; the binding cap shows in the `agent.skill_round_cap` span attribute, the resolution Info log, and the hint's `(skill cap: <name>)` suffix (uncapped turns render byte-identical strings). Negative → skill rejected at `skill.ParseFile`, so every surface inherits the validation. Design: `design/archive/sprint-2026-08/3-skill-max-tool-rounds-plan.md`.
- **`configmcp.BuildSkillPayload` is the only frontmatter writer** behind every skill CRUD surface (config MCP, external MCP, REST) and rebuilds the block from a fixed struct — **any field missing from it is silently erased** the first time a skill is updated or patched. `MergeSkillFields` must therefore carry every non-edited field through; `max_tool_rounds` and `requires.tools` both do, and `TestMergeSkillFields_PreservesAllFieldsOnBodyOnlyEdit` + `TestSkillPatch_PreservesRequiresAndRoundCap` are the canaries. A new frontmatter field needs **five** edits: the `frontmatter` struct, `Skill`, `BuildSkillPayload`'s local `fm`, `MergeSkillFields` (nil/absent = keep), and the create/update inputs on all three surfaces — plus `just openapi` for the REST pair. Slice-valued inputs follow the `triggers` convention (absent = keep, `[]` = clear); **table-valued** fields (`requires`) must stay last in `fm`, since a TOML table header captures every key declared after it.
- **`requires.tools` gates skill *inclusion* (fail-inactive), not tool *exposure***: `Engine.filterUnsatisfiedSkills` drops any matched skill naming a tool absent from `Manager.ToolNames()`. Evaluated **per message**, so a skill goes inactive when its MCP server drops and reactivates on the next message after it returns — no restart, no reload, no event plumbing (the registry is the liveness signal: the health checker unregisters a failed server's tools and re-registers on restart). It runs immediately after `MatchSkills` and its output **is** `matchedSkills`, so the prompt section, round-cap resolution (`drivingSkill`), telemetry attribution and skill-usage bumps all share one inactive semantics — an excluded skill cannot drive a turn, cap rounds, or be recorded as used. `e.tools == nil` → no filtering (no capability information; never guess); names match **verbatim**, same convention as auto-approve rules; a skill with no declared tools is always satisfied. Exclusion covers a schedule-driven skill too (`msg.SkillName`) — injecting prose whose tools 404 burns a round — and that case Warns **per occurrence**, since a silently skipped scheduled run is an operational failure. All other deactivate/reactivate logging is **once per state change**, keyed by a sorted missing-tool signature in `Engine.skillSatisfaction` (an ambient skill matches every message and would otherwise warn on every turn). The existing "scheduled skill not found" Warn is deliberately evaluated against the *pre-filter* set, so exactly one accurate warning fires: not-found vs deactivated. Still **not** enforced: which tools are *advertised* to the model — that is finding **B2** (`design/agent-ops-findings-2026-07-14.md`, plan in `design/plans/2-requires-tools-enforcement.md`), which composes rather than overlaps, gating exposure at request time where this gates inclusion at match time — and unknown names are still accepted at save time, so the runtime filter is the enforcement. Tests: `internal/agent/engine_skill_satisfaction_test.go`.
- **Tool-loop wrap-up on model-behavior stops** (unconditional, no config knob): when the loop stops due to repeated identical tool calls (threshold 3) or `maxToolRounds` exhaustion with a *healthy* context, the engine does NOT fail the turn — it appends synthetic tool results for suppressed calls, then issues one final **tools-stripped** completion (`Router.CompleteFinal`, `Tools: nil` on the wire) to summarize executed work. Fallback: wrap-up text → accumulated intermediate content → error into `persistInterruptedProgress` (still the path for transport faults). Content carries `[engine: turn ended early — <reason>]`; the wrap-up round audits `wrap_up: true` (no `round` field). A third stop reason, `stopRequested`, shares this exit but skips the wrap-up completion — see "Step-boundary stop" below. Design: `design/archive/loop-guard-wrapup-round.md`.

- **Step-boundary stop (panic)**: `executePanic` raises a cooperative stop on **every** engine (`Engine.RequestStop`) *before* the `inFlight` context sweep. The signal is a monotonic `stopGen` counter, captured per turn into `turnRun.stopGen` — self-scoping ("end everything running now"), so nothing resets it and a turn starting later is unaffected. `runToolLoop` checks it at the top of each round and `runRoundToolCalls` before each call in a round: the call in flight always finishes (bounded by `toolExecTimeout`) and keeps its real outcome, un-started calls get synthetic tool messages (`appendSyntheticResults`, shared with the repeat-abort path) and **no** `ToolCallRecord` — a never-attempted call must not read as a tool fault. Exit is the new `stopRequested` `loopStopReason` → `finishStoppedTurn`, which unlike the model-behavior stops issues **no** wrap-up completion (no spend during an emergency stop), sits *above* the no-records guard (so a stopped turn never leaves a dangling user message), and persists through the normal `persistTurn`. Because the flag is engine-scoped, WS/SSE/REST/MCP-chat/scheduled turns observe it too even though they are never in `inFlight` — but only inside a tool loop, and only for panic: `/stop`, `POST /sessions/{id}/stop` and the WS cancel frame are still context-kill only. Stage 1 of `design/plans/6-step-boundary-stop.md` (which carries the entry-path coverage table and the remaining stages: approval cancel, scheduler, stop scoping). Origin: the same review against "A Programming Paradigm for Spatiotemporal Composability" (Shi, Zhang, Cui — https://github.com/cordiverse/paper/blob/main/paper.pdf) that produced the tool-name qualification and the skill undo journal; a mid-step kill leaves an effect set the runtime cannot state the extent of, which is what makes `internal/skilleffect` unable to mean anything at turn granularity. The boundary is the fix for that gap, not something the paper prescribes.

- **Within-turn tool-call memoization**: identical (name+args) calls to *idempotent* tools return the round-N cached result instead of re-executing — no execution, no approval/supervisor round-trip (the original call already passed approval; a hit executes nothing). Cache lives in `turnToolState` next to the denial dedup map, dies with the turn, only `Outcome == "ok"` results enter it. Result is prefixed `[engine: identical call — cached result from round N]`; record `Outcome: "cached"` (excluded from fault counts and duration averages, counted in `cached_count`); audit `cache_hit` without the result body. Idempotency via `Manager.IsIdempotent`: in-process tools use the code-constant allowlist (`kv_get`, `kv_list`, `web_fetch`, `web_search`; deliberately not `run_javascript` or configmcp reads), external tools opt in via `[tools.*]` `idempotent = true` (whole server) / `idempotent_tools = [...]` (mixed servers), or `trust_annotations = true` to extend eligibility to tools the server marks `readOnlyHint` (captured at discovery into `serverConn.readOnlyHinted`; `idempotentHint` deliberately ignored — it permits state-changing first calls) — hints are never trusted without that per-server operator opt-in. The repeat-abort detector observes cached hits upstream, so 3 identical calls still trip the wrap-up. Read-after-write staleness (kv) is accepted for v1; invalidation out of scope.

Other errors keep their own codes (400 malformed/rejected, 500 failed restart/removal, 503 lifecycle manager unwired). New tool endpoints follow the same wrap-and-classify pattern.

- **`run_javascript` (Script MCP)**: in-process per-agent tool running short JS (goja, pure-Go ES5.1) against JSON `input` — fresh VM per call, no host globals (no network/fs/require). `[script]` bounds: `timeout` (2s, via `vm.Interrupt` + ctx cancel), `max_output_chars` (16000, truncates), `max_input_bytes` (262144, rejects), `max_concurrent` (4) — a process-global semaphore built once in main.go and shared across all agents' `Deps`; negative = unbounded. `max_concurrent_per_agent` (0 = off) adds a per-agent semaphore; `acquireSlot` takes per-agent then global in fixed order (no deadlock), releases in reverse. Disabled in `restricted` tier. Residual risk: no per-VM heap cap — `max_concurrent` bounds the multiplier (~`max_concurrent × rate × timeout`) but is not a hard memory ceiling.
- **`ExecPolicy` is the whole isolation mechanism for non-live turns** (`internal/agent/execpolicy.go`; Stage A of `design/eval-subsystem.md`). A non-nil policy on `chatWithApproval` switches one turn to dry-run/eval semantics; nil is the untouched live path, so a user who never previews anything sees no behavioral change. Bundled with the round budget in `turnRun` and threaded down the tool loop. What it changes: **conversation** = `policy.ConvID` verbatim, no row created (`resolveConversation` short-circuits); **history** = `policy.History` verbatim if set, else `policy.HistoryFrom` read-only, both strictly *preceding* the turn, neither = fresh turn (see the pinned-history bullet below); **the message itself** = appended to the wire explicitly by `prepareTurn` (`assembleMessages`' `currentTurn` argument), because a live turn only reaches the model via the store-then-read-back round trip that a policy turn skips — without it the request is a system prompt with **zero** user turns and the model invents a prompt to answer, so previews measure hallucination rather than the skill; **persistence** = `persistTurn` returns immediately, so no messages, telemetry, stats, nudges, or reviewer — isolation is structural, not filtered; **approvals** = `supervised` is forced false in `runToolLoop`; **tools** = `IsIdempotent` executes live, everything else (including unknown tools — fail closed) returns the `outcomeSuppressed` marker before reaching the approval chain or `Manager.Execute`; **clock** = `policy.AsOf` pins `buildSystemPrompt`'s `## Current Date`. Suppressed results deliberately do **not** enter the within-turn memo cache (nothing executed, so there is no round-N result to serve). `ToolCallRecord.Arguments`/`.Result` are `db:"-"` in-memory-only fields — safe because `AddToolCalls` inserts an explicit column list — and are the seed of L1 trace capture.
- **Model overrides clone the router, never mutate it**: `ExecPolicy.Model` is applied via `llm.Router.WithModel` (a shallow copy sharing providers, cost tracker, pricing and fallbacks — only `defaultModel` differs), resolved once into `turnRun.router` and threaded through **every** completion in the turn including `completeToolRound`, `wrapUpToolLoop` and `recoverEmptyToolResponse`. `Router.SetDefaultModel` must not be used for this: the router is shared by every turn on an agent, so mutating it would silently retarget a live turn already in flight, and a turn that started on a candidate must not finish on the live model. `turnRun.router` is non-nil on any turnRun reaching a completion (zero values are fine for the tool-execution helpers, which read only `policy`); a nil there panics loudly, which is the wanted failure mode for a construction bug. `TurnResult.RequestedModel` carries the asked-for model beside the `Model` that answered, so a transcript is self-describing without consulting agent config. **Provider overrides work the same way**: `ExecPolicy.Provider` → `llm.Router.WithProvider`, composed with `WithModel` in `routerFor` (`e.router.WithModel(m).WithProvider(p)`); each call returns the receiver unchanged when its override is empty or already current, so an eval run's incumbent variant talks to the engine's own router and costs nothing. The clone does **not** reject an unknown provider name — callers accepting an overlay should ask `Router.HasProvider` up front, since failing at request time would fail every sample instead of the run creation.
- **Pinned history (`ExecPolicy.History`) beats live history (`HistoryFrom`)**, checked first in `loadTurnHistory` and returned verbatim with `truncated=false` (the caller bounded it when it captured it). The two answer different questions: `HistoryFrom` names a live conversation and reads its *most recent* window at turn time, which is right for "preview this against whatever the session looks like now"; `History` replays a snippet captured earlier, which is what a saved eval task needs, because the source conversation drifts (`ClearMessages` empties it but keeps the row, retention prunes it) and its latest window is not the window that preceded the saved message. A test case that silently re-scopes itself between runs is not a test case. Only `Role`/`Content` are read — the other `StoredMessage` fields are ignored by `assembleMessages` and may be left zero.
- **Eval runs execute on *live* engines, and that is a deliberate divergence** (`internal/eval/`, Stage B of `design/eval-subsystem.md`). `Runner` resolves `Dispatcher.Agent(base_agent)` and calls `Engine.DryRun` per sample with an `ExecEval` policy; it never builds an engine. The design doc §4.4 named the reviewer-engine pattern, but that engine is capability-*reduced* (fresh tool manager, no shared MCP tools, no auditor), so every tool-path metric on one would measure a different system than the one in production — and a per-run *full*-capability rebuild would be a drift-prone copy of `buildAgentEngine`. Safety comes from elsewhere: isolation is `ExecPolicy`'s structural guarantee (the eval path never reaches the persistence layer), and the variant overlay is a per-turn `WithModel`/`WithProvider` router clone, so nothing on the live engine is mutated. main.go's `EngineSource` adapter **must nil-check the `*agent.Engine` before boxing it** into `eval.Engine` — a typed nil in an interface reads as non-nil.
  **Cancellation is three layers deep because eval turns are never in `dispatcher.inFlight`** (only the adapter message loop registers there): `Runner.Stop(id)` cancels the run context, `StopAll()` hangs off main.go's `OnPanic` closure, and the engine-scoped `RequestStop` sweep independently ends any eval turn at its next tool-round boundary. There is deliberately **no** `OnResume` counterpart — a panic is not a pause, and a stopped run stays stopped. All bookkeeping (status writes, sample rows, cost, lifecycle audit) uses a `context.WithoutCancel` copy, because the ordinary way a run ends *is* its context being cancelled: sharing one context would leave a stopped run wedged at `running` forever, which is exactly the bug the split exists to prevent.
  **Cost is read from `CostTracker.SessionCost(policy.ConvID)`, never `TurnResult.CostUSD`** — the latter is provider-reported and only OpenRouter writes it, so a cap keyed on it would never trip on Anthropic/OpenAI/Ollama. This is also why the sample conversation id carries the **variant**: `eval:{run}:{task}:{k}:{variantID}` (`eval.SampleConvID`), one level deeper than the design sketch. The id doubles as the cost tracker's session key, so two variants of one `(task, k)` sharing it would bill the second for the first's spend — enough to trip the cap early and to report a running total as a per-sample figure.
  **`capped` ≠ killed**: the cap is checked *before* each dispatch, so a sample already in flight always finishes (it is paid for and its result is data); the run then finishes `capped` with partial results retained. A `DryRun` error with a live context fails **that sample only** (`status = failed` + the error text) — a run-level `failed` means a store error, never a provider hiccup. Sample rows record `outcome_cached` and `outcome_suppressed` as their own columns; folding either into `outcome_failed` would poison the failed-rate gate, and an eval turn suppresses writes routinely. Aggregation excludes both from the rate denominator (nothing executed) and reads `stop_reason` as **slugs**, never the prose `String()` forms. Per-task deltas are baselined against the **first variant by creation order** — convention only, unenforced.
  Scopes are `eval:read`/`eval:write` (runs write nothing real but spend real tokens, same reasoning as the dry-run endpoints). `adminScopes()` in `internal/api/auth.go` is hand-maintained and **not** derived from `scope.Names()`, so a new scope missing from it locks dashboard sessions out with no test failure.
- **`loopStopReason` has two renderings and they must not be merged**: `String()` is prose baked into the user-facing `[engine: turn ended early — <reason>]` marker and must stay byte-identical; `slug()` is the machine-readable form (`repeated_calls`/`max_rounds`/`stop_requested`, empty for `stopNone`) that reaches `TurnResult.StopReason` and the dry-run transcript's `stop_reason`. The reason is threaded out of the loop as a 4th return from `runToolLoop`→`executeToolRounds`→`runLLMWithTools` onto `turnOutcome.stopReason`; the live chat path ignores it (a live user already gets the honesty marker in the response text), so only `DryRun` reads it. Before this it died inside `executeToolRounds` and the only way to detect a cut-short turn was scraping the marker out of the response body.
- **Audit marking travels in the context, not the policy**: `policy.mark()` builds an `agentctx.ExecMark` installed once per turn; `Engine.emitAudit` applies it. The cost tracker also registers the pseudo-agent, so preview spend never lands in a real agent's totals.

It is a shared `.chip` inside a `.filter-chips` container paired with a `.filter-label`, **not** a bare button appended to `.filters` — that container is a `48px 1fr` grid of label/control pairs, so a direct child lands in the narrow label column and renders as a wrapped blob. - **Skill dry-runs pick an invocation, not always a message**: `mode` ∈ `schedule`/`command`/`message`, resolved by `resolveSkillMode` (explicit wins → a non-empty `message` keeps message semantics → `command:` trigger → a schedule naming the skill → else `message`). The modes differ in more than text: only `schedule` sets `msg.SkillName` (which is what forces body injection) and `IsScheduled`; `command` and `message` leave `SkillName` empty so ordinary trigger matching runs, so a command preview exercises the trigger rather than bypassing it. Before this, the handler set `SkillName` *and* used a typed message with `IsScheduled: false` — a hybrid matching neither real path, which is why a scheduled skill previewed that way wasn't testing what happens when it fires.
- **Ambient ≠ scheduled, and frontmatter cannot tell them apart** (#305): a triggerless skill matches *every* turn and reads the user's own text; it is scheduled only if `[[schedules]]` names it. The inference therefore consults `Scheduler.Entries()` (`Server.schedulesForSkill`, agent-scoped with the same empty-`Agent`→fallback resolution `handleDryRunSchedule` uses, sorted — `Entries()` walks a map), and a skill with neither trigger nor schedule defaults to `message`. Explicit `mode:"schedule"` on an unscheduled skill still works (a hypothetical) and keeps the synthesised header. `GET /skills` and `/skills/{agent}` carry `scheduled_by` (omitted when nothing schedules the skill) — that is the **only** signal `SkillInvocation.svelte` has to preselect the right chip.

- **Skill undo journal** (`internal/skilleffect/`, table `skill_revisions`): every runtime skill mutation on all three surfaces is journaled *before* it happens, so `skill_revert` can undo it. Layering is `agent ← configmcp ← skilleffect` — the four `configmcp.Apply*` helpers are unchanged and the effector is a layer above them; **`configmcp` therefore must not import `skilleffect`** and instead receives a `configmcp.SkillWriter` implementation on `Deps` (nil = untracked passthrough via `directSkillWriter`, which is also what a store lacking the revision methods degrades to). REST/external MCP obtain theirs by type-asserting `Deps.Memory` to `skilleffect.Store`. Ordering is **read prior bytes → append revision → write** and fail-closed: a failed append aborts the mutation, because journal-before-write leaves at worst an idempotent no-op revision while write-before-journal leaves an untracked mutation. `prior_payload` is the **raw on-disk bytes** (never re-serialized through `BuildSkillPayload`, which would drop unknown frontmatter fields), NULL meaning "the file did not exist" — which is what makes every NULL-prior inverse a removal. Restores go back through `configmcp.SkillPayloadFromFile` to strip the trailer `writeSkillFileAtomic` appends; without it every undo would grow the file by one newline. At-most-once is the conditional `UPDATE … WHERE reverted_at IS NULL` in `MarkSkillRevisionReverted` (claimed iff RowsAffected == 1) — race-free and restart-proof — and reverts **claim before applying**, so a crash mid-revert loses one undo rather than double-applying. A revert is itself journaled with `actor='revert'`, so undo-the-undo is free and **two reverts in a row redo the original change** rather than stepping further back (the tool description says so). Transitions revert LIFO (`seq DESC`): a rename followed by an update must be undone update-then-rename or the update targets a name that no longer exists. `prior_version`/`new_version` join against `tool_calls`/`by_tool_skill`, **not** the version-less `skill_usage`. Actor per surface: config MCP `self`, REST and external MCP `user`. A payload that will not parse, or a name `ValidateSkillName` rejects, is never journaled. Out of scope (deliberately): per-turn transition ids threaded from the engine, an auto-revert curator (which must never auto-undo an `actor='revert'` row, or it oscillates), config-MCP/REST revert surfaces, retention.
- **Skill-file IO confined via `os.Root`**: all skill writes/removes in `configmcp` go through an `os.Root` on `agentSkillsDir` (`openSkillRoot` + `writeSkillFileAtomic`) — OS-level refusal of `..` traversal and escaping symlinks, backstopping `ValidateSkillName` (the shared denylist enforced in the write helpers on every surface: REST, config MCP, external MCP). REST/external-MCP read the cap via `skillMaxBytes()`; config MCP via `Deps.MaxSkillBytes`. Fuzz-tested (`FuzzApplySkillCreate_NeverEscapes`); concurrency `-race` tested.
- **OpenAPI spec is a gated generated artifact**: `internal/api/docs/swagger.json` is committed (`//go:embed`-ed, served at `/api/v1/openapi.json`) and must match handler annotations. `just openapi-check` regenerates into a throwaway dir and diffs — never mutates the tree, deliberately uncached. After touching an annotated handler: `just openapi` and commit. Gotcha: `swag` only reads an annotation block **directly attached** to its handler func — a blank line or intervening declaration silently drops the endpoint from the spec.
- **Shared validators** (`internal/config`): `ValidResourceName`, `ValidProviderType`, `IsProviderReferenced` — use for new CRUD endpoints.
- **`internal/agentctx`**: context-key package shared between `agent` and `configmcp` to avoid an import cycle; use it to thread agent identity through MCP handlers.
- **Date/week injection (two-point)**: the model never infers "today". (1) Scheduled messages render fire time via `scheduler.FormatScheduledText` — `[Scheduled: heartbeat | 2026-07-07T10:45:00+10:00 Australia/Sydney | 2026-W28]` — computed in the fire callback (both producers: `registerSchedules`/`buildScheduledMessage` in main.go and `configmcp.BuildScheduleJob`), `msg.Timestamp` from the same instant. (2) `buildSystemPrompt` appends `## Current Date` at **day resolution by design** (a clock time would bust the prompt cache every turn). Timezone precedence: agent `timezone` > `api.timezone` > UTC (`agentLocation` in main.go; engine knob `SetLocation`, hot-reloaded). Cron *evaluation* stays `api.timezone` and restart-only. Midnight-crossing runs can see header date ≠ prompt date — the fire-time header wins for dated keys.
- **`web_fetch` page size** (`[web.fetch] max_response_chars`, default 8000, valid 1..100000): chars of converted Markdown per call; the tool description formats the live value so the model can plan pagination. Restart-only like all `[web]` settings (webmcp is built once per agent at startup; `buildReloadFunc` re-applies only per-agent engine knobs). Also editable in the Server Config UI / `PATCH server/config` (`web_fetch_max_response_chars`, bounds re-checked in the handler, `restart_required` flagged on change). Writer note: `updateTopLevelSection` merges sub-table values key-by-key — required because `[web.fetch]` is a sub-table and a wholesale replace would clobber `timeout`/`user_agent` siblings.
- **Released-PR stamping** (`stamp-prs` in `release.yml`): comments the version on each released PR; resolves commits→PRs via the GitHub API (`commits/{sha}/pulls`), not `(#N)` subject parsing (mixed merge strategies break parsing).
