# Audit log invariants

- **The hash preimage is frozen** (`chainHash`, `internal/audit/chain.go`, #587): the tag `denkeeper.audit.v1`, then id, timestamp, category, action, agent, summary, detail, status, duration_ms, source, conversation_id and prev_hash, each as an 8-byte big-endian length plus its raw bytes. Changing a field, the order or the encoding fails every existing row. A change needs a new tag and a way to tell row versions apart. `TestChainHash_GoldenVectors` pins it. The timestamp is hashed as the exact stored text (formatted once at insert), never a re-parsed `time.Time`; `detail` is hashed as raw bytes and never re-marshalled; a NULL `duration_ms` hashes as an empty field, which no integer formats to, so it differs from `0` and every non-NULL row hashes as before (inserts never write NULL, so NULL means an edit).
- **`id` is chain order, not `timestamp`.** `Emit` stamps the time, and two producers can enqueue in a different order than they stamped.
- **Two readers, two costs.** `List` counts a total and pages with `LIMIT`/`OFFSET` in timestamp order, so walking n rows page by page costs about n²/page rows: fine for a screen, not for a scan. `ScanEvents` streams every match in id order in one query, with no total, limit or offset; a caller that needs time order sorts what it kept (`CountUnsafeApprovals` does). Its callback must not touch the store: the in-memory store has one connection and the open query holds it. Both take `ListOpts` timestamps formatted as text and compared as text, so pass UTC bounds; a local-zone bound misfilters.
- **Every append goes through `appendChained`**, under `SQLiteStore.chainMu`, in a write transaction that reads the head (`readChainHead`) first. The file DSN has `_txlock=immediate`, so a second process waits for the write lock before it reads the head; without it the loser fails with SQLITE_BUSY and the batch is lost (`TestChain_TwoHandlesOnOneFile`). Nothing caches the head. A head with an empty hash (a legacy row, or an empty table) starts a new chain with an empty `prev_hash`. The in-memory store has no `_txlock` and is pinned to one connection (`SetMaxOpenConns(1)`), since each `:memory:` connection is a separate database. A query outside the transaction during a write therefore waits for that one connection, so queries inside a write must use the transaction, and tests that write concurrently use a file store.
- **Prune deletes an id prefix and writes its checkpoint in the same transaction** (`PruneBefore`): everything below the first id still inside retention, then one `audit`/`prune_checkpoint` row whose detail carries `pruned_rows`, `pruned_through_id`, `pruned_through_hash` and `cutoff`. Deleting by timestamp alone would punch holes in the chain. A sweep that deletes nothing writes nothing. The checkpoint links to the pre-prune head, not to the last deleted row.
- **Migration is two `ADD COLUMN ... NOT NULL DEFAULT ''`** in `auditMigrations` (duplicate-column errors swallowed). No backfill: verify counts unhashed rows before the first hashed row as legacy ("not covered") and starts the chain there. An older binary still writing to a migrated file produces unhashed rows, which verify reports as `unhashed_row` until retention prunes the chained rows before them; they then read as a legacy prefix (`TestVerifyChain_RollbackBreakHealsAfterRetention`).
- **`VerifyChain` is on `*SQLiteStore` only**, never the `Store` interface. It runs in one read-only transaction and stops at the first break: `hash_mismatch`, `link_mismatch`, `unhashed_row`, or `missing_start` (the first chained row has a `prev_hash` that no checkpoint's `pruned_through_hash` accounts for). A checkpoint vouches for the start only when it is itself inside the verified chain (`checkCheckpointStart`), and unhashed rows below a checkpoint start are a break, since a prune deletes the oldest ids first; otherwise an unhashed planted row could vouch for a deleted prefix. That check runs only when the walk found no break of its own: a specific break the walk found is reported as is. `OpenSQLiteStoreReadOnly` opens with `query_only` and runs no schema or migration.
- **List surfaces do not hide `audit` rows.** Checkpoints and `dropped_events` rows are ordinary events: REST, the external MCP `audit_events`/`audit_summary` tools and the dashboard show them, and they count in stats. The config-MCP `approval_audit` tool is fixed to `supervisor` and `approval`, so an agent never sees them. Hashes are not on `audit.Event`, so `swagger.json` does not change.
- **Limits, stated as such in the docs** (tamper-evident, not tamper-proof): removing the newest rows, a full rewrite with recomputed hashes, and a forged checkpoint all verify, because the hash has no secret; edits to legacy rows are not covered. Keeping verify's head line off the machine is the only defence today.
- **The emitter records its own losses** (T2): events refused by a full buffer and events in a failed `InsertBatch` are counted, and the flush goroutine writes one `audit`/`dropped_events` row itself, when the channel is empty (tick, `Flush`, shutdown), never through the channel. A failed flush that carried the record restores the counts.
