# Adapter invariants

- **Telegram activity log**: tool approvals render inline in the activity-log message (collapsible blockquote) with buttons, not as separate messages. Every size budget in `dispatcher.go` counts **rendered, HTML-escaped** bytes, never source text (`&` → 5 bytes, `<`/`>` fourfold). Budgets sum-bounded by construction: blockquote gets `activityChunkMaxBytes` (3000) alone or `activityChunkWithApprovalMaxBytes` when sharing with an approval; approval section gets `approvalSectionMaxBytes`; `truncateEscaped` enforces shares; `setPending` starts a fresh chunk if no room. Over-cap sends are rejected by Telegram — with an approval attached that silently loses the keyboard, so those failures log Error (`activityLog.logSendFailure`, `sendDebugApprovalPrompt`, `sendStandaloneApprovalPrompt`); cosmetic activity-log failures stay Debug.
- **High-risk approval prompts** (#586, `ChatEvent.ApprovalRisk`): all three paths (activity log, standalone, debug) render `newRiskBlock` once, in this order: header, the warning line written in code, one line per flagged argument, then the arguments block; buttons are Approve and Deny only (`promptButtons`). The risk block replaces `humanOnlyApprovalNote`, which says the same; `tool_add`/`plugin_add` are always high-risk, so the note now shows only for a human-only call without a risk. The risk block is budgeted by `approvalRiskMaxBytes` (1400 escaped bytes, markup included), **carved out of** `approvalArgsMaxBytes` (`approvalArgsBudget` gives the arguments block the other 600), so `approvalSectionMaxBytes` and every bound derived from it are unchanged. Flagged values are **never cut**: a partial value could hide the part that makes the call risky, and the model could otherwise push it past a cut by padding. When the block does not fit, it becomes the warning plus `riskTooLongLine` (review in the dashboard, or deny), the HTML header reads "— review in the dashboard" instead of "— approve?" (the debug header is neutral and stays), the prompt drops "Approve once or deny." and "Approve?", and the only button is Deny. Too-long holds when **either** rendering is over the budget: HTML escaping grows `<`, `>` and `&`, and the markdown grows backtick runs, so neither bounds the other. **Debug fences**: both fenced blocks (flagged lines and arguments) go through `breakBackticks`, which puts a zero-width space between adjacent backticks, so a value's ``` cannot close the fence and have Discord render the rest as markdown (a fake approve line, a masked link); the arguments are broken **before** `truncateEscaped`, so the added bytes count toward the budget. A harmless prompt is byte-identical to before (`TestApprovalPrompt_HarmlessCallRendersAsBefore`).
