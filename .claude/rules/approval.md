## Permission Tiers & Approval Workflows

Tiers: `autonomous` (all actions), `supervised` (chat + tools with approval), `restricted` (chat + read-only tools).

**The restricted tier's read-only grant**: `security` maps a tier to `use_tools` (every advertised tool) or `use_read_only_tools` alone (restricted). `agent.grantFor` turns that into a `toolGrant` resolved once per turn onto `turnRun.grant` — zero value `grantNone`, so a turnRun that never passed the permission check executes nothing. `executeToolCall` checks the grant **first**, ahead of the dry-run policy and the approval chain, and a call the grant refuses is denied one at a time rather than failing the turn: record `Outcome: "denied"` / `ErrorMsg: "denied (read-only tier)"`, a `denied`-status `tool_call` audit event, tool_start/tool_end events, and an `[engine: call not executed — …]` result the model answers around. It deliberately does **not** enter the per-turn denial dedup map (the gate re-answers a repeat for free) and never reaches an approval — a restricted agent has no approval path to escalate to. Classification is `tool.Manager.IsReadOnly`: the in-process `builtinReadOnlyTools` allowlist (wider than the memoization one — `skill_get` is read-only but must not be cached), or, for external servers, `idempotent`/`idempotent_tools` (documented as "only servers whose tools are ALL read-only") or `readOnlyHint` under `trust_annotations`. Conservative by construction: an unclassified tool, an ambiguous name, and every tool when no manager is wired are all not read-only. Which tools are *advertised* to a restricted agent is unchanged — that is finding B2, gating exposure rather than execution.

`internal/approval/` manages human sign-off. Flow: Engine submits → Manager persists + registers closure → inline Approve/Deny keyboard → callback resolves → closure invoked. Eleven action kinds: `user_update`, `soul_update`, `identity_update`, `create_skill`, `update_skill`, `delete_skill`, `modify_schedule`, `install_tool`, `modify_config`, `browser_profile`, `tool_call`.

**Supervised tool calls**: each MCP call needs approval. Engine checks `Manager.ShouldAutoApprove()` first (match → immediate execution, `tool_approval` event with `auto_approved`), else blocks on `WaitForResolution`. Dispatcher sends four buttons: Approve, Deny, Auto (session), Auto (always). Denied calls feed "Tool call was denied by the operator." to the LLM. Within one turn, a name+args exact match against an already-denied call is auto-denied (status `auto_denied`); dedup map resets on next user message.

**Auto-approve rules**: three scopes, checked `config` → `session` → `permanent`. `session` (in-memory, conversation-scoped, 15m TTL) and `permanent` (SQLite, agent-scoped) are created at runtime from Telegram buttons (`:approve_session`/`:approve_always`), web UI Always Approve, or REST; `approval.ExtractToolName()` keys them from the approval summary. `config` is declared per agent in TOML (`[[agents]] auto_approve_tools = [...]`), held in memory on the Manager, and **replaced wholesale** by `SetConfigRules` — the only writer, called from the config-load path (startup + `POST /server/reload`). It cannot be weakened at runtime: `POST /auto-approve` 400s on `scope: "config"`, config rules are listed with an empty `id` so DELETE has nothing to address, and `RemoveAutoApproveRule`/`ClearSessionRules` touch different state. Ordering cannot change an approve/deny outcome (all three answer the same question) — it fixes **attribution** (`scope=config` stays stable across sessions) and skips the SQLite lookup for the hottest calls. Newly-blessed pairs auto-resolve queued approvals, same as the other two scopes. Validation is syntax-only at load (non-empty, no whitespace, unique — `ValidResourceName` deliberately not applied, MCP names have hyphens); names not matching an advertised tool are **warned about at wiring/reload and kept**, never dropped (a late-connecting remote server must not silently weaken policy). Stage-1 auto-approvals emit an `audit.CategoryApproval` / `auto_approve` event with `detail.scope` for **all** scopes.

**No scope covers a high-risk call** (#586). The table is `internal/toolrisk` (a leaf package, standard library only): `tool_add`, `plugin_add` and `set_fallback` always; `schedule_add` with a non-empty `session_tier`; `schedule_update` with `session_tier` present, even `""` (clearing an override can raise a schedule pinned below its agent; `null` reads as absent, like the handler's `*string`); `persona_update` for `soul`/`identity` after trim and lower-case. `toolrisk.Classify` decodes the arguments into per-tool structs with the config-MCP handlers' JSON tags, so an exact duplicate key resolves to the value the handler acts on (last wins); never scan a map for exact key names. A **case-variant** key does not: `tool.Manager.ExecuteResult` re-encodes the arguments through a `map[string]any` with sorted keys, so `section` and `Section` (or `ſection`, U+017F) both reach the handler, which reads whichever sorts last, while the struct decode may have read the other. So any top-level key that `strings.EqualFold`-matches a field an entry reads (`entry.reads`: `section`/`content` for `persona_update`, `session_tier` for the schedule tools) without being spelled exactly like it fails closed (`hasCaseVariant`), whatever the SDK's encoder does; a conditional row with a new field must list it in `reads`. Arguments that do not parse are high-risk with the raw text flagged (fail closed). Classification is by advertised name (bare or `<server>__<tool>`), so an external tool of the same name is treated the same. `approval.Manager` enforces it in three places, so no surface can forget it: `ShouldAutoApprove` takes the call's arguments and answers no for a high-risk call before any scope, **config included** (TOML cannot bless one; startup and reload warn about an `auto_approve_tools` entry for an always-high tool, `warnHighRiskAutoApprove`); `AddSessionRule`/`AddPermanentRule` return `ErrHighRisk` and store nothing for an always-high tool; and a rule from a pending request is refused **before the request resolves** (`CheckStandingRule` for REST/WS, the same check inside `ResolveByCallback` for session/always presses), so it stays pending for a plain Approve or Deny. That refusal applies to `tool_call` requests only: an `install_tool` request (#600's human-only `tool_add`/`plugin_add`) never becomes a rule, so an auto press still approves it once. Every refusal emits `create_rule` with status `denied` and `detail.reason = "high_risk"`. `autoResolvePending` skips a high-risk request, so a rule made from a harmless `schedule_update` never approves a queued one that sets a tier. Every request the manager returns carries a derived `Risk` (never stored), and `ListAutoApproveRules` marks a rule for an always-high tool `Inert`: rules stored before #586 stay in the database and never apply. The engine puts the same classification on the pending event (`ChatEvent.ApprovalRisk`, absent otherwise). The decider and supervisor can still approve a high-risk call that is not human-only.

**Supervisor agents**: `supervisor = "agent-name"` on a supervised agent inserts an LLM reviewer between auto-approve and human approval: APPROVE / DENY (reason fed to LLM) / ESCALATE (→ human). One-shot LLM call via the supervisor's Router with tool details + recent history — no storage/skills/tool loops. Emits `audit.CategorySupervisor` events and `tool_approval` statuses `supervisor_approved`/`_denied`/`_escalated`/`_error` (error falls through to human). Web UI: supervisor controls in Agents, statuses in Chat, filter chip in AuditLog.


## Invariants

- **Human-only tools need an operator in every tier** (DEN-82): `tool.Manager.RequiresHumanApproval` (in-process tools `toolrisk.HumanOnly` names: `tool_add`, `plugin_add`; an ambiguous name answers by `IsHumanOnlyToolName`) sends the call to `Engine.resolveHumanOnlyApproval` from `executeToolCall`, ahead of and **instead of** the supervised chain, including in `autonomous`. It skips auto-approve rules, the decider and the supervisor, and fails closed (`denied`) with no approval manager or no event handler (headless schedules). The request is submitted as `ActionKindInstallTool`, not `tool_call`: every rule-creating path (`createAutoApproveFromCallback`, WS `auto_*`, REST `?auto_approve=`) and `autoResolvePending` act on `tool_call` only, so no button or later rule can answer one. `ChatEvent.ApprovalHumanOnly` makes the dispatcher (`approvalButtons`) and the web chat drop the 15 min / Always buttons and add one line saying why (`humanOnlyApprovalNote`, counted in `approvalSectionOverheadBytes`; the same sentence as a `.hint` on the dashboard), unless the event's risk block is shown, which says the same (#586). These tools are always high-risk, so in practice their prompts show the risk block (`adapters.md`). The Chat page's polled banner has no human-only field on the REST row, so it keys on `kind`: it lists `tool_call` rows and `install_tool` rows whose summary `parseToolCall` reads (an engine tool call, i.e. a human-only `tool_add`/`plugin_add`; config MCP's own "Install tool: …" rows stay on the Approvals page), and shows the auto-approve buttons only for `tool_call`. `POST /auto-approve` 400s for these names. A config-MCP tool that spawns code on the host must be added to the `toolrisk` table with `humanOnly`.

- **`aborted` is a fifth terminal status, written only by `Manager.Abort`**: the turn waiting on the request stopped at a step boundary, so nothing will ever answer it. Not a denial (the operator refused nothing, and the LLM must not be told it was denied) and not expired (nothing timed out); leaving it pending is the orphan the step-boundary stop exists to prevent. `Abort` drops the registered closure without running it and notifies waiters with `StatusAborted`. The engine calls it from `awaitToolApproval` on a `context.WithoutCancel` copy, since the stop may arrive with a context kill behind it. Surfaces: `ValidStatus`, the `?status=` filter, the Approvals page filter row, and the `aborted` `tool_approval` event status. Stage 4 of `design/plans/6-step-boundary-stop.md`; the engine-side contract is in `agent-engine.md`.
- **Resolution audit follows the action**: `Resolve` and `ResolveByCallback` share `settle`, which runs the approved action *then* emits the `approve`/`deny` event, so a failed action is `status=error` with `detail.error`, and returns `ErrActionFailed` (row already approved — callers must not report it as unresolved). `AddSessionRule`/`AddPermanentRule` emit `create_rule` with `detail.scope`, covering every surface (Telegram, REST, WS).
- **Supervisor config validation**: supervisor must exist, must not itself be supervised (no chaining), must not use `supervised` tier (deadlock), and `supervisor` is only valid on supervised agents. Both tier checks resolve an empty `session_tier` to `[session] tier` (`effectiveTier`), the tier the engine runs under. Delete guard rejects removing a referenced supervisor; rename rewrites other agents' `supervisor` and `[[channels]] agent` (TOML, in-memory snapshot, live channel registry). Reload re-wires `supervisor =` on running agents (`reconcileSupervisor`; a named supervisor that is not running is cleared, so calls go to a human). The engine holds the supervisor and its five knobs atomically, with 0 meaning default, so reload and a PATCH that clears a knob both restore its default. `supervisorReview` takes the supervisor it was handed and never re-reads the field mid-review. `supervisor_timeout` is a Go duration string; `supervisor_context_messages` int (0 = default 5).
- **Decider stage** (`supervisor_decider`, `internal/agent/supervisor_decider.go`, #444): a `[[llm.deciders]]` decision model scores each supervised call between auto-approve and the supervisor. It asks seven noul questions, all with yes meaning the hazard is present (`off_task`, `overreach`, criterion 2 of `writeSupervisorEvalCriteria` split into `injection`/`secrets`/`sends_external`/`private_data`, and `self_grant` for criterion 4), and `deciderChecks` combines them into six checks where high means safe (`aligned` = 1 − off_task, `scoped` = 1 − overreach, `no_leak` = 1 − sends_external × private_data, `no_self_grant` = 1 − self_grant). Question ids and check ids are deliberately different strings: the yes-is-safe `aligned`/`scoped` questions they replaced scored benign calls ~0.65, and `isLegacyDeciderAnswers` recognises those reviews by their `aligned` answer key. `no_leak` is in `deciderEscalateOnlyChecks`: it blocks approval but never denies, because a legitimate send of private data (emailing the user their own tasks) cannot be told apart from a leak without the supervisor. `no_self_grant` is escalate-only too, because its wording has not been calibrated against the model: a low score hands the call to the supervisor, whose criterion 4 denies calls that save a permission for the agent (text saying it may act without asking, a claimed operator or user approval, or an instruction to skip review; approval comes from config, never chat). It is deliberately the same test as `self_grant`, so a user's own request to create or schedule a skill is not denied. Promoting it to a denying check is one line once `denkeeper decide replay` justifies it. **Write targets**: for the in-process skill and KV write tools (`skill_create`/`update`/`patch`/`write_file`/`delete`, `kv_set`, `kv_delete`; `Engine.ResolveWriteTarget`, `writetarget.go`) both stages read a `target` — whether the skill or key exists and, for a key, when and by which scheduled skill it was last written (only scheduled turns carry a skill context, so other writes read "not recorded"; see the KV writer stamp in `agent-engine.md`). The supervisor sees one `**Target**:` line after the arguments plus a sentence on criterion 3; the decider gets `target` in its state; both audit details carry it. A call with no target renders no target line and no `target` key, but criterion 4 is in every review prompt. An external server's tool of the same name gets no target (`tool.Manager.BuiltinLocalName` plus a match on the local name). Skill existence is checked the way `skill_create`'s handler checks it, a loaded skill **or** a file on disk (`Engine.SetSkillFileCheck`, wired to `configmcp.SkillFileExists` in `buildAgentEngine`), so a create the handler will refuse never reads as a fresh one; a lookup error gives no target. `skill_update` with a `new_name` different from `name` is action `rename`, carrying `new_name` and `new_name_exists`. Each tool's target is decoded from **only** the argument its handler reads (`writeToolSpec.argKey`: `skill` for `skill_write_file`, `name` for the other skill tools, `key` for KV); reading any other field lets a decoy argument make an overwrite of a live skill read as a fresh create, so a new write tool must name its handler's field. `last_written_by` records which scheduled skill's turn wrote the key and authenticates nothing. Names, keys and the writer are model-chosen text and go through `%q`. `ShadowReview.MinDenyScore` (`min_deny_score`) carries the lowest deny-eligible check for the web panel, whose `verdict` mirrors this. Both `decideSupervisorOutcome` and `shadowReviewFrom` read only `deciderChecks`, so verdict and calibration cannot drift. `shadowReviewFrom` skips reviews holding the old single `safe_args` answer or the old yes-is-safe `aligned` answer (`isLegacyDeciderAnswers`), so earlier question sets never reach calibration. A review missing **only** `self_grant` predates that question and is scored on the five checks it has (`onlySelfGrantMissing`), while the live `decideSupervisorOutcome` still escalates when `self_grant` is missing; the audit events themselves are kept until retention removes them. `sends_external` judges from the tool description, so lowering `supervisor_tool_desc_len` below a tool's network sentence (`run_javascript`'s sits past character 300) blinds it. `shadow` mode (default) emits a `CategorySupervisor` event with `source = "decider:<name>"`, `decision = "shadow"` and `would_decide`, and never changes the outcome or emits a ChatEvent of its own; its verdict rides on the later `tool_approval` events as `shadow` (display only, never fed into a decision), which the Telegram and Discord adapters ignore. `enforce` mode acts on `decideSupervisorOutcome`: APPROVE runs the call without asking the supervisor, DENY feeds `Tool call denied by decider: <reason>` to the model, ESCALATE goes on to the supervisor (or, with none, emits `supervisor_escalated` and waits for a human). It reuses the `supervisor_*` `tool_approval` statuses with text naming the decider, and its audit `decision` is the verdict itself with no `would_decide`. `runSupervisorDecider` returns `ok = false` in shadow mode and on every failure, and the caller ignores the verdict unless `ok`, so a failed decider can never approve. `resolveSupervisedApproval` reads `!ok` while enforcing as a decider failure for telemetry (see the outcome split in `agent-engine.md`), so a new `ok = false` path that is not a failure must change that. Decider and supervisor read one `supervisorReviewInput` (markdown vs JSON rendering) so their views cannot drift, except the skill body: the decider gets `deciderSkillBodyLen` (12000), because skills prescribe exact `run_javascript` code past the 500-char excerpt and Jev cannot judge alignment without it. The two renderings also mark an external server's tool description differently (#584): the supervisor's markdown puts it inside T1's `<untrusted_tool_output source=… id=…>` tags under a label (`writeToolDescription`, framed after the `supervisor_tool_desc_len` cut so the closing tag survives); the label quotes the block's real closing tag, because the supervisor's system prompt is its persona and never gets T1's same-id note, while the decider's JSON keeps the description as is and sets `tool.description_untrusted` — the questions were not reworded, because wrapping would shift the calibrated `sends_external` scores, and no question reads the flag yet. The supervisor's recent-conversation header now says the history is context only. Neither stage sees tool results, so nothing else is framed there. Spend is keyed `decider:{name}:{reviewed}:{convID}` and billed to the **reviewed** agent (unlike the supervisor). Failure causes add `too_large`: input over `max_input_tokens`, or over the model's default-mode budget (`llm.Decider.WithinDefaultMode`, Jev ~32 KB, from `defaultModeBytes` in `internal/llm/decision.go`; add a model there when switching deciders). Never truncated, and never fitted by shrinking the skill excerpt: padded arguments would crowd out the evidence `off_task`/`overreach` are judged against while approval stays possible. The eval judge shares the decider and keeps the full `max_input_tokens`. Deciders live in an `llm.DeciderSet` (`api.Deps.Deciders`): `Sync` rebuilds it from `[[llm.deciders]]`, keeping the same `*Decider` for an unchanged entry so rebinding is a no-op, and each decider looks its provider up in the shared `ProviderSet` on every call (`NewLiveDecider`), so a rotated key needs no rebuild and a missing or chat-only provider fails as `provider_error`. Reload runs `syncDeciders` (`cmd/denkeeper/deciders_live.go`) before building new agents: it syncs the set and calls `bindSupervisorDecider` for every running agent, binding, switching or clearing the stage. `PATCH /agents/{name}` binds from the same set and 400s only when the named decider is not in it. Calibration (`GET /agents/{name}/decider-reviews`, MCP `decider_reviews`, the Permission panel's chart) loads through `agent.LoadShadowReviews` and pairs shadow reviews with supervisor reviews in `agent.PairShadowReviews`: same conversation, tool and arguments, supervisor review within 15 min after, FIFO for duplicates. There is no shared call id in either event, so changing what either stage writes as `arguments` breaks the pairing. The Agents nav badge is **shadow mode only** (`handleDeciderReviewCounts` skips enforce-mode agents, whose decider acts instead of being compared). It counts unsafe approvals (decider would approve, supervisor denied or escalated) after a per-agent, per-decider review mark in `audit.db` (`decider_review_marks`, Unix-nanosecond time because RFC3339Nano text does not sort within a second; a time outside 1677-09-21 to 2262-04-11 would wrap, so `audit.ReviewMarkInRange` refuses it in the store and `parseUpTo` answers 400). It reads the whole window, unlike the reviews list's 10k cap, so a busy agent is not undercounted, in one `audit.Store.ScanEvents` pass (id order, no total, no OFFSET) that keeps a few fields per event (`countEvent`, the pairing key SHA-256-hashed) rather than events with their Detail. It pairs through `pairQueue`, the same FIFO-within-15-min queue `PairShadowReviews` uses, and both sort by time with ties in event id order, so badge and panel pair identically **for the events both scan** (`TestCountUnsafeApprovals_AgreesWithThePanelsPairing`, `TestPairShadowReviews_SameTimestampOrderedByID`). They can still differ in what they scan: past the panel's 10k cap the badge counts reviews the panel does not list, and the badge's window starts 15 min before the mark. Only `POST .../decider-reviews/reviewed` ("Mark all reviewed") moves the mark, and only forward; opening the panel does not. The memoized count carries a per-agent generation that a mark bumps, so a count already reading when the mark landed is answered but not cached, and concurrent counts for one agent, decider and thresholds share one scan (`deciderCountRuns`, run on `context.WithoutCancel` so one caller hanging up cannot fail the rest, bounded instead by `deciderCountScanTimeout`, 1 min; a timed-out or panicking scan releases its run with an error and is never cached, so the next poll counts again). The panel never moves its mark back: a reload that read the older mark before its own POST landed keeps the later one. The panel measures the 15-minute pairing window on the response's `until`, the server's clock, not the browser's, reloads when this agent's badge count changes (except the drop its own mark caused), and announces nothing while loading. The count uses `ShadowReview.Verdict`, which must stay in step with `decideSupervisorOutcome` (`TestShadowReviewVerdict_MatchesDecideSupervisorOutcome`), and loads from 15 min before the mark so an earlier verdict cannot pair with a later identical call. A supervisor review records `cost` from `ChatResponse.BilledUSD` (router-resolved; `CostUSD` is provider-reported only), and events written before that have none, which the panel shows as unknown. The web panel's verdict rule (`web/src/deciderCalibration.js`) mirrors `decideSupervisorOutcome`. Hazard: `CostTracker` remembers one provider per session key, so a decider moved to another provider keeps the old provider's limits until its session key rolls. `denkeeper decide replay` (`cmd/denkeeper/decide.go`) re-scores past supervisor verdicts through `agent.ReplaySupervisorDecider`, which reuses this stage's state rendering, questions and threshold policy; it audits nothing and has no tool description, guidance or skill context to send.
- **Supervisor review spend is billed per conversation, to the supervisor's agent** (`supervisorSessionKey`, which carries the reasoning): the key is `supervisor:{reviewed}:{convID}` and is registered with the cost tracker under the supervisor's own name. Both halves are load-bearing and neither is inferable from the call site — a process-constant key makes the per-session `cost_limit_hard` a lifetime budget that nothing resets (every review then fails closed to a human until restart), and skipping `RegisterSessionAgent` bills a phantom agent named `supervisor`, which also skips the real agent's configured limits. A failed review records `detail.cause` (`cost_limit`/`timeout`/`provider_error`/`too_large`) since all causes land on the same `supervisor_error` status. `too_large` = arguments over `supervisor_max_args_bytes`, rejected before any LLM call. The cap gates the supervisor stage only; the decider has its own `max_input_tokens` guard, so it can still decide a call above the supervisor's cap.
- **A schedule's `session_tier` never exceeds its agent's tier unless the operator set it** (`configmcp.ValidateScheduleTier`, `security.TierExceeds`). Config MCP and external MCP always enforce it, against the writing agent's tier for config MCP and the target agent's for external MCP, even with an admin key. REST enforces it unless the key has `admin`. TOML is the operator and is not checked. The engine still honours any valid override (`resolvePermissions`), so the cap lives on every write surface: a new schedule write path must call it. Config MCP also refuses to edit a schedule already above the agent's tier, and a move to another agent needs an explicit tier (an empty one runs at the target's) capped at the target's tier too, via `Deps.AgentTier`; nil refuses the move. Fail closed: an unrecognised tier counts as exceeding, since the engine ignores it and falls back to the agent's own tier.
