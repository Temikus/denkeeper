# Skill & config-MCP invariants

- **Two frontmatter writers, one per path** (#423), reached only through configmcp on every surface (config MCP, external MCP, REST): `BuildSkillPayload` → `skill.RenderNew` creates (always TOML, `+++`); `MergeSkillFields` → `skill.Render` edits in the skill's own dialect (config MCP `skill_patch` goes through it too, body only). Keys Denkeeper does not read are kept. When no field changed, the raw block is reused byte for byte (minus blank lines just inside the delimiters, which `splitBlock` trims); otherwise YAML is a node edit (a changed value is a fresh node, so its quoting is not kept) and TOML a map rewrite. A rewrite that would change the set of unknown keys fails with `skill.ErrUnknownKeysChanged`, which `explainRenderError` turns into "the edit was not saved … Edit <file> by hand" (`<folder>/SKILL.md in the skills directory` for a directory-form skill, relative so REST and MCP callers never see the server's absolute path; else "the skill's file in the agent's skills directory", since a flat skill does not record its path); surfaces prefix `building skill: `, and REST answers 422 for it (`skillRenderStatus`), 500 for any other render failure. Both delimiters must be lines of their own (`splitBlock`), so `+++` or `---` inside a one-line value never ends the block. The **first** delimiter line always wins: a hand-written TOML multi-line string holding a line that is exactly `+++` is refused, never re-split at a later line, because a splitter that differs from other TOML readers lets a downloaded skill hide keys they would show as body. The writers never emit that shape (go-toml escapes newlines). **Directory-form skills** (`<skills dir>/<name>/SKILL.md`): every write, read and remove resolves the file by name through `skillFileRel` (`<name>.md` if present, else `<name>/SKILL.md` if that folder exists), so edits, the journal's prior bytes and reverts all hit SKILL.md. A delete removes only SKILL.md and leaves the folder's other files; `SkillFileExists` (which #531's write `target` reads) counts that leftover folder as taken, so `skill_create` refuses it rather than inheriting the old files, while a revert of the delete writes back into it (`RefuseExistingSkillForRestore`/`ApplySkillRestore`, chosen in `Effector.Create` by actor `revert`). Renaming one is refused (`ErrSkillNotEditable`, REST 422), since the journal cannot move a folder back, and so is editing one whose folder is not named after the skill (`MergeSkillFields`), which would otherwise write a second, flat copy. `LoadDir` warns when two files define one skill name (e.g. `kelos.md` beside `kelos/SKILL.md`); both load, and writes go to the flat one. `MergeSkillFields` must still carry every non-edited field through; `TestMergeSkillFields_PreservesAllFieldsOnBodyOnlyEdit`, `TestSkillPatch_PreservesRequiresAndRoundCap`, `TestMergeSkillFields_YAMLBodyOnlyKeepsBlockBytes` and `TestSkillPatch_YAMLKeepsFrontmatterBytes` are the canaries. A new frontmatter field needs **six** edits: the `frontmatter` struct, `Skill`, `skill.Fields` with the `knownKeys` list (both dialect writers read it; a key missing from it is treated as unknown, so it is preserved but never updated), `MergeSkillFields` (nil/absent = keep), the create/update inputs on all three surfaces, and the TOML structs in `frontmatter.go` — plus `just openapi` for the REST pair. Slice-valued inputs follow the `triggers` convention (absent = keep, `[]` = clear); **table-valued** fields (`requires`) must stay last in `tomlKnown`, since a TOML table header captures every key declared after it; a new scalar also goes into `tomlKnownScalars`. `max_output_tokens` (#432) shares its name and unit with the agent and global knob from #561. Like `max_tool_rounds`, it is written only when non-zero and applies only when one skill drives the turn; it lowers the effective cap (the agent's, else `[llm]`'s), and when neither is set the skill's value is sent as is (see the `max_output_tokens` bullet in `agent-engine.md`).
- **`configmcp.LintSkillWrite` runs before every skill write** on all three surfaces (plus config-MCP `skill_patch`): it rejects a `schedule:<name>` trigger naming no existing schedule, and warns when the body changed without a version bump or a scheduled skill lacks `max_tool_rounds`. Triggers carried over unchanged from the prior skill are exempt, so a legacy skill stays editable. A new write path must call it.
- **Config MCP tools** (in-process per-agent set, not REST): `schedule_update`, `schedule_delete`, `set_fallback`, `get_cost_summary`, `skill_delete`, `channel_list`, `channel_switch`, `channel_info`, `approval_audit`, `ops_report`.
- **`ops_report` is the calling agent's own data only** (`ops_tools.go`, #436): gated on `Deps.OpsReport` **and** a non-empty `AgentName`; the agent comes only from `Deps.AgentName` and the input decodes `days` alone, so an `agent` argument is ignored and the clock (`opsreport.Query.Now`) is never an argument. All numbers come from `opsreport.Build`, shared with the external MCP tool. Telemetry (spend, tools, skills) is scoped through `conversation_stats.agent`, so a shared channel conversation moved from one agent to another carries the earlier agent's aggregates with it — the tool description says so. `actual_fires` reads `session`/`trigger` audit events with source `scheduler` and `detail.schedule_name` (`TestOpsReport_ReadsWhatTheEngineWrites` is the canary for that shape). `CostTracker` and `schedule`/`fire` events are deliberately not read: they have no agent. On `builtinReadOnlyTools` (restricted and dry-run turns run it), not `builtinIdempotentTools`. Not given to the reviewer (`reviewerConfigDeps`). `spend.change_pct` is `null`, never omitted, when the earlier window had no spend. Wired in `connectConfigMCP` with `opsScheduleSource`, which keeps a nil scheduler a nil interface.
- **`approval_audit` scope is fixed server-side** (`audit_tools.go`): `ListOpts.Agent = Deps.AgentName` (exact match, so `#dryrun`/`#eval` pseudo-agents are excluded too) and categories are only `supervisor`/`approval`; neither comes from input. Gated on `Deps.AuditStore` **and** a non-empty `AgentName`. Detail is projected to a key allowlist (`cause`, `reason`, `decision`, `tool`, …) rather than truncated, because detail JSON sorts `arguments` first and a cut would drop `cause`. A shadow decider review's verdict is hidden: `would_decide` is off the allowlist, and `redactShadow` replaces the summary and drops `reason`. `search` therefore runs in Go over the redacted events (newest 2000), never as the store's `summary LIKE`, which would answer "which calls would jev deny". Limit 20 default, 100 max. Wire it with `auditReader` in main.go: a nil `*audit.SQLiteStore` in the interface passes a nil check.
- **Config MCP registration is dep-gated, and that is the capability boundary**: every tool is registered only when the dependency its handler dereferences is present on `Deps` (`registerSkillTools`/`registerScheduleTools`/`registerLifecycleTools` + the per-tool gates). An absent dep means the tool is **not advertised at all**, not advertised-then-erroring. Consequence: a dep that stops being wired silently removes a tool rather than producing a readable error — `TestRegisterTools_NewlyGatedToolsPresent` is the canary. `Server.tier()` fail-closes to `restricted` when `PermissionTier` is nil. `persona_update` gates on `SavePersonaSection` and `persona_memory_manage` builds its `operation` enum from whichever of `AppendMemoryEntry`/`RemoveMemoryEntry`/`SavePersonaSection` are present — the advertised schema is the capability statement.
- **External MCP skill tools** (`tools_skills.go`): `skill_create`/`skill_update`/`skill_delete` are **disk-first** — create/update/rename write via `configmcp.ApplySkill*` (now through the effector, same ordering) then mutate memory; delete checks `GetSkill` → file removal (fail-loud) → `RemoveSkill`, so an IO error leaves the skill intact. Persist failure → `toolError`, memory unchanged. REST `handleDeleteSkill` matches (500, not 204, on IO error). `skill_update` supports optional `version` and `new_name` (rename). `validSkillName` rejects path separators and `..`. `skill_revert` (`skills:write`) undoes the newest armed revision for a skill, for a `transition_id`, or agent-wide — see the skill undo journal below.
- **Skill undo journal** (`internal/skilleffect/`, table `skill_revisions`): every runtime skill mutation on all three surfaces is journaled *before* it happens, so `skill_revert` can undo it. Layering is `agent ← configmcp ← skilleffect` — the four `configmcp.Apply*` helpers are unchanged and the effector is a layer above them; **`configmcp` therefore must not import `skilleffect`** and instead receives a `configmcp.SkillWriter` implementation on `Deps` (nil = untracked passthrough via `directSkillWriter`, which is also what a store lacking the revision methods degrades to). REST/external MCP obtain theirs by type-asserting `Deps.Memory` to `skilleffect.Store`. Ordering is **read prior bytes → append revision → write** and fail-closed: a failed append aborts the mutation, because journal-before-write leaves at worst an idempotent no-op revision while write-before-journal leaves an untracked mutation. `prior_payload` is the **raw on-disk bytes**, so a revert restores the dialect, comments and formatting exactly (pinned for YAML by the `TestEffector_Revert_YAML*` tests), NULL meaning "the file did not exist" — which is what makes every NULL-prior inverse a removal. Restores go back through `configmcp.SkillPayloadFromFile` to strip the trailer `writeSkillFileAtomic` appends; without it every undo would grow the file by one newline. At-most-once is the conditional `UPDATE … WHERE reverted_at IS NULL` in `MarkSkillRevisionReverted` (claimed iff RowsAffected == 1) — race-free and restart-proof — and reverts **claim before applying**, so a crash mid-revert loses one undo rather than double-applying. A revert is itself journaled with `actor='revert'`, so undo-the-undo is free and **two reverts in a row redo the original change** rather than stepping further back (the tool description says so). Transitions revert LIFO (`seq DESC`): a rename followed by an update must be undone update-then-rename or the update targets a name that no longer exists. `prior_version`/`new_version` join against `tool_calls`/`by_tool_skill`, **not** the version-less `skill_usage`. Actor per surface: config MCP `self`, REST and external MCP `user`. A payload that will not parse, or a name `ValidateSkillName` rejects, is never journaled. Out of scope (deliberately): per-turn transition ids threaded from the engine, an auto-revert curator (which must never auto-undo an `actor='revert'` row, or it oscillates), config-MCP/REST revert surfaces, retention.
- **Skill-file IO confined via `os.Root`**: all skill writes/removes in `configmcp` go through an `os.Root` on `agentSkillsDir` (`openSkillRoot` + `writeSkillFileAtomic`) — OS-level refusal of `..` traversal and escaping symlinks, backstopping `ValidateSkillName` (the shared denylist enforced in the write helpers on every surface: REST, config MCP, external MCP). Requires Go ≥ 1.24.
- **Skill write hardening**: randomized temp name (`.skill-<rand>.tmp`, `O_EXCL`) + `Root.Rename`, so concurrent writers can't share/corrupt a temp file. Per-file cap `[skills] max_bytes` (1 MiB default; negative = unlimited), enforced inside `ApplySkill*` (`checkSkillPayloadSize`) — skill content is written verbatim and would otherwise be an unbounded-write DoS. REST/external-MCP read the cap via `skillMaxBytes()`; config MCP via `Deps.MaxSkillBytes`. Fuzz-tested (`FuzzApplySkillCreate_NeverEscapes`, which tries every name as both a TOML and a YAML payload); concurrency `-race` tested. YAML frontmatter adds its own refusals at parse, so they hold on every surface: anchors, aliases and merge keys (no amplification, no dangling alias on write), duplicate keys at any level, and explicit tags; a parser or encoder panic is recovered into an error.
