# Eval & dry-run invariants

- **`ExecPolicy` is the whole isolation mechanism for non-live turns** (`internal/agent/execpolicy.go`; Stage A of `design/eval-subsystem.md`). A non-nil policy on `chatWithApproval` switches one turn to dry-run/eval semantics; nil is the untouched live path, so a user who never previews anything sees no behavioral change. Bundled with the round budget in `turnRun` and threaded down the tool loop. What it changes: **conversation** = `policy.ConvID` verbatim, no row created (`resolveConversation` short-circuits); **history** = `policy.History` verbatim if set, else `policy.HistoryFrom` read-only, both strictly *preceding* the turn, neither = fresh turn (see the pinned-history bullet below); **the message itself** = appended to the wire explicitly by `prepareTurn` (`assembleMessages`' `currentTurn` argument), because a live turn only reaches the model via the store-then-read-back round trip that a policy turn skips — without it the request is a system prompt with **zero** user turns and the model invents a prompt to answer, so previews measure hallucination rather than the skill; **persistence** = `persistTurn` returns immediately, so no messages, telemetry, stats, nudges, or reviewer — isolation is structural, not filtered; **approvals** = `supervised` is forced false in `runToolLoop`; **tools** = `IsIdempotent` executes live, everything else (including unknown tools — fail closed) returns the `outcomeSuppressed` marker before reaching the approval chain or `Manager.Execute`; **clock** = `policy.AsOf` pins `buildSystemPrompt`'s `## Current Date`. Suppressed results deliberately do **not** enter the within-turn memo cache (nothing executed, so there is no round-N result to serve). `ToolCallRecord.Arguments`/`.Result` are `db:"-"` in-memory-only fields — safe because `AddToolCalls` inserts an explicit column list — and are the seed of L1 trace capture.
- **Model overrides clone the router, never mutate it**: `ExecPolicy.Model` is applied via `llm.Router.WithModel` (a shallow copy sharing providers, cost tracker, pricing and fallbacks — only `defaultModel` differs), resolved once into `turnRun.router` and threaded through **every** completion in the turn including `completeToolRound`, `wrapUpToolLoop` and `recoverEmptyToolResponse`. `Router.SetDefaultModel` must not be used for this: the router is shared by every turn on an agent, so mutating it would silently retarget a live turn already in flight, and a turn that started on a candidate must not finish on the live model. `turnRun.router` is non-nil on any turnRun reaching a completion (zero values are fine for the tool-execution helpers, which read only `policy`); a nil there panics loudly, which is the wanted failure mode for a construction bug. `TurnResult.RequestedModel` carries the asked-for model beside the `Model` that answered, so a transcript is self-describing without consulting agent config. **Provider overrides work the same way**: `ExecPolicy.Provider` → `llm.Router.WithProvider`, composed with `WithModel` in `routerFor` (`e.router.WithModel(m).WithProvider(p)`); each call returns the receiver unchanged when its override is empty or already current, so an eval run's incumbent variant talks to the engine's own router and costs nothing. The clone does **not** reject an unknown provider name — callers accepting an overlay should ask `Router.HasProvider` up front, since failing at request time would fail every sample instead of the run creation.
- **Pinned history (`ExecPolicy.History`) beats live history (`HistoryFrom`)**, checked first in `loadTurnHistory` and returned verbatim with `truncated=false` (the caller bounded it when it captured it). The two answer different questions: `HistoryFrom` names a live conversation and reads its *most recent* window at turn time, which is right for "preview this against whatever the session looks like now"; `History` replays a snippet captured earlier, which is what a saved eval task needs, because the source conversation drifts (`ClearMessages` empties it but keeps the row, retention prunes it) and its latest window is not the window that preceded the saved message. A test case that silently re-scopes itself between runs is not a test case. Only `Role`/`Content` are read — the other `StoredMessage` fields are ignored by `assembleMessages` and may be left zero.
- **Eval runs execute on *live* engines, and that is a deliberate divergence** (`internal/eval/`, Stage B of `design/eval-subsystem.md`). `Runner` resolves `Dispatcher.Agent(base_agent)` and calls `Engine.DryRun` per sample with an `ExecEval` policy; it never builds an engine. The design doc §4.4 named the reviewer-engine pattern, but that engine is capability-*reduced* (fresh tool manager, no shared MCP tools, no auditor), so every tool-path metric on one would measure a different system than the one in production — and a per-run *full*-capability rebuild would be a drift-prone copy of `buildAgentEngine`. Safety comes from elsewhere: isolation is `ExecPolicy`'s structural guarantee (the eval path never reaches the persistence layer), and the variant overlay is a per-turn `WithModel`/`WithProvider` router clone, so nothing on the live engine is mutated. main.go's `EngineSource` adapter **must nil-check the `*agent.Engine` before boxing it** into `eval.Engine` — a typed nil in an interface reads as non-nil.
  **Cancellation is three layers deep because eval turns are never in `dispatcher.inFlight`** (only the adapter message loop registers there): `Runner.Stop(id)` cancels the run context, `StopAll()` hangs off main.go's `OnPanic` closure, and the engine-scoped `RequestStop` sweep independently ends any eval turn at its next tool-round boundary. There is deliberately **no** `OnResume` counterpart — a panic is not a pause, and a stopped run stays stopped. All bookkeeping (status writes, sample rows, cost, lifecycle audit) uses a `context.WithoutCancel` copy, because the ordinary way a run ends *is* its context being cancelled: sharing one context would leave a stopped run wedged at `running` forever, which is exactly the bug the split exists to prevent.
  **Cost is read from `CostTracker.SessionCost(policy.ConvID)`, never `TurnResult.CostUSD`** — the latter is provider-reported and only OpenRouter writes it, so a cap keyed on it would never trip on Anthropic/OpenAI/Ollama. This is also why the sample conversation id carries the **variant**: `eval:{run}:{task}:{k}:{variantID}` (`eval.SampleConvID`), one level deeper than the design sketch. The id doubles as the cost tracker's session key, so two variants of one `(task, k)` sharing it would bill the second for the first's spend — enough to trip the cap early and to report a running total as a per-sample figure.
  **`capped` ≠ killed**: the cap is checked *before* each dispatch, so a sample already in flight always finishes (it is paid for and its result is data); the run then finishes `capped` with partial results retained. A `DryRun` error with a live context fails **that sample only** (`status = failed` + the error text) — a run-level `failed` means a store error, never a provider hiccup. Sample rows record `outcome_cached` and `outcome_suppressed` as their own columns; folding either into `outcome_failed` would poison the failed-rate gate, and an eval turn suppresses writes routinely. Aggregation excludes both from the rate denominator (nothing executed) and reads `stop_reason` as **slugs**, never the prose `String()` forms. Per-task deltas are baselined against the **first variant by creation order** — convention only, unenforced.
  Scopes are `eval:read`/`eval:write` (runs write nothing real but spend real tokens, same reasoning as the dry-run endpoints). `adminScopes()` in `internal/api/auth.go` is hand-maintained and **not** derived from `scope.Names()`, so a new scope missing from it locks dashboard sessions out with no test failure.
- **Pairing is a run-finalization step, and it runs for `capped`/`stopped` too** (`internal/eval/pairing.go`, Stage C). `Runner.finalizePairs` calls `Store.CreatePairs` after `dispatch` returns and before `FinishRun`, so a terminal run arrives at the judge queue already populated — there is no separate "prepare for judging" call to forget. Only `StatusFailed` is skipped (nothing was dispatched). It is **idempotent by guard** (a run with pairs is left alone) and a pairing error never changes the run status: the samples are recorded and the objective scorecard stands alone. A `(task, k)` whose sample is missing or `failed` on **either** side yields no pair, which is why `Completeness` carries `pairs`/`pairs_judged` next to the sample figures — a run can be sample-complete with holes in the judging grid. **N > 2 variants pair every candidate against the baseline** (first by creation order, same convention as per-task deltas), not round-robin: the question the rule answers is "is this candidate an upgrade on the incumbent", and nothing consumes candidate-vs-candidate (resolves §11.4 with option (a)).
- **Blinding is three indirections deep, and the payload is built rather than filtered.** `eval_pairs.assignment` maps letter→variant and is the *only* unblinding key; `eval_judgment_items.presentation_order` (`ab`/`ba`, two per pair) says whether the pair's A or B was shown first; a verdict names a **presented** letter. `VariantFor(assign, order, winner)` is the single resolver. `Store.GetBlindedItem` constructs `BlindedItem`/`BlindedResponse`/`BlindedToolCall` field by field from `agent.ToolCallRecord` **instead of embedding or filtering the stored structs** — blinding that removes fields fails open the day a column is added, and this must fail closed. Scrubbed: variant name, model, provider, upstream (the provider-reported serving upstream stored on the sample), cost, latency, token usage, tool-call duration (a consistently slower side is an identity hint), and the `eval:{run}:{task}:{k}:{variant}` conversation id. `TestGetBlindedItem_LeaksNoIdentity` serialises the payload and greps for every one of them; **the fixture's own response text must stay neutral**, or it trips its own canary. The A/B coin is `crypto/rand`, per pair, and panics rather than falling back — a seeded sequence a judge could reproduce would unblind the whole run, and a silent fallback would blind nothing while looking like it did.
- **A pair counts only when both presentation orders carry a judge verdict, and disagreement is a tie** — resolved at *aggregation* time (`resolvePairs`), never at write time, since a judge working the queue must not see the other order's call. Naming the same presented letter twice resolves to two different variants, i.e. the judge tracked position, so the pair records a tie. A half-judged pair is not evidence and stays out of the tally entirely. Verdicts are unique per `(item_id, judge_ident)` (SQLite unique index + upsert), so a retrying headless judge overwrites its own call rather than inflating the count. **The operator's calibration marks are ordinary verdicts with `judge_ident = "operator"`** (zero schema change): they sit *alongside* the judge's rather than replacing it, are excluded from the win rate, feed only the agreement figure, and deliberately do **not** flip an item to `judged` — an item only the operator has seen is still outstanding judge work.
- **The decision rule is conjunctive and asymmetric** (`internal/eval/verdict.go`). Order: thin data (`!Completeness.Conclusive`) → `inconclusive`; any failed gate → `downgrade` naming it; nothing judged → `no_regressions`; win-rate ≥ `win_threshold` → `upgrade`; else `downgrade`. The gates alone can **never** promote — "cheap and quiet" is not "better" — and a judge preference can never override an objective regression. Every verdict carries its work: the three-row gate table (value, delta, threshold, unit `pp`/`%`, pass), a one-line prose `Reason`, the per-category breakdown, and `Divergence` ("wins overall; regresses on tool_heavy") which is **surfaced, not gated**. A zero-value `SummaryOpts` takes the shipped defaults via `withDefaults` — a zero threshold would fail every gate — which is why `Summarize` takes the struct rather than a bare float. `percentGate` passes when the baseline is 0: there is no ratio to take, and an honest "cannot say" beats a fabricated infinity.
- **The two acquisition paths are different axes, and `category` is what keeps them apart** (`internal/eval/suggest.go` vs `probes.go`, Stage D3 and Stage E item 2). `Suggest` mines history bottom-up; `GenerateProbes` reads written intent top-down (permission tier, auto-approve policy, persona sections, skill frontmatter) and files everything under `CategoryProbe`. Folding probes into `chat`/`tool_heavy` would let a regression on *specified* behaviour hide inside a chat win rate, which is the one thing the per-category breakdown exists to prevent. `Categories()` is the full axis (five) and drives `DrawStratified` plus the results breakdown; **`HistoryCategories()` is the four `Suggest` can actually produce** — stratifying over all five would reserve a share for a family that pass can never fill. `GenerateProbes` takes a narrow `SpecSource` that `*agent.Engine` satisfies as it stands (the `InterestingTurnStore` narrowing, same reasoning), is a **pure function of the spec** — deterministic, which is the only reason `ProbeOpts.Exclude` keyed on *prompt* is enough to keep a repeat pass quiet — and spreads a `Limit` across families round-robin so a cap never truncates a family away. Session-scoped auto-approve rules are excluded from `ProbeOpts.AutoApproveTools`: they expire, and a probe built around a rule that vanishes in fifteen minutes grades a policy the agent no longer has. Denial-compliance probes carry the refusal in `Preceding` (pinned history is `{role, content}` only, so a tool result cannot be replayed — the assistant states the denial in its own words); the dry-run policy's `suppressedResult` says "assume success" and is **not** a denial, so it cannot stand in for one. Family caps (`probeFamilyCap`) are applied **after** `Exclude`, not while building the family: capping first would pin the skill family to the same few skills forever, so accepting what was offered would leave a repeat pass with nothing new and the skills past the cap unprobed. `approvalProbes` is **supervised-only** — autonomous has no approval gate and restricted has no `use_tools` permission, so the engine blocks the call before policy is consulted, and a probe there would grade the candidate against a rule it is not under. A probe quotes configuration back (a skill's description, the auto-approve list), so `GET /eval/probes` requires `agents:read` alongside `eval:read` and drops the `skill_instruction` / `approval_policy` families via `ProbeOpts.SkipKinds` for callers without `skills:read` / `tools:read` — generating from config must not become a way around the scope that guards reading it. Probe `Notes` are free-text judge context — §2's no-DSL decision stands, and nothing reads them back.
- **`Deps.EvalStore` on the *external* MCP server is the judge surface and deliberately omits the runner** (`internal/mcpserver/tools_eval.go`, mirroring `tools_audit.go`'s store/emitter split). A key scoped `eval:read`/`eval:write` can read blinded pairs and write verdicts; it cannot create, start or stop a run, which is the right shape given runs spend real tokens. `eval_verdict` is the only writer among the five tools. Unconfigured → `toolError("eval not configured")`, never unregistered. `judge_ident` defaults to the API key name (`keyNameFromCtx`) so verdicts are attributable without the caller remembering. Unknown dimension names are **rejected**, not stored: a typo that silently vanishes from the results table is worse than a failed call. The `/judge-eval` skill lives at `.claude/skills/judge-eval/SKILL.md` and is the **one** thing under `.claude/` that is not gitignored (`.claude/*` + `!.claude/skills/`) — the rubric is a repo deliverable and has to travel with the code it grades.
- **Trace capture is opt-in for live turns and unconditional for eval samples, and the engine never persists one** (`internal/agent/trace.go`, `internal/eval/trace.go`, Stage E item 1 of `design/eval-subsystem.md`). `Engine.buildTurnTrace` assembles the payload — built system prompt, the wire history minus the leading system message, the per-round tool calls *with* `Arguments`/`Result` (the `db:"-"` fields' only durable home), the raw model response — and runs for a policy turn always, for a live turn only when `[eval] capture` is on **and** a sink is wired (`SetTraceCapture` + `SetTraceSink`, both re-applied on hot-reload; `TraceCaptureEnabled` requires both). `saveTurnTrace` refuses on `policy.active()`, so an eval sample's trace reaches the store through `Runner.saveSampleTrace` off `TurnResult.Trace` rather than through the engine — the persistence boundary stays exactly where `persistTurn` draws it. The trace records `responseText`, not `out.response`: on a withheld reply the point is what the model produced. A sink error is logged and swallowed; a turn that answered the user is not failed by bookkeeping.
  **Truncation drops oldest-first and says so**: rounds, then history messages, then a last-resort clamp of the long text fields, with `TracePayload.Truncation` carrying the counts and a prose note. `maxBytes <= 0` means the default 256 KiB — there is deliberately no "unbounded", since one pathological turn would otherwise fill the table. `config.DefaultMaxTraceBytes` and `agent.DefaultMaxTraceBytes` are stated independently (config must not import agent) and pinned equal by `TestTraceCapDefaultsAgree` in main.
  **`turn_traces` sits in the eval schema but the rows are ordinary turns**, and `eval_samples.trace` stays beside it answering a different question (the sample's tool path for the judge, versus the whole turn including the prompt). New table, so `CREATE TABLE IF NOT EXISTS` is the migration and no `evalMigrations` entry exists. Retention is its own `[eval] retention_days` (30, matching audit) on the shared audit cleanup cadence — these are the most sensitive rows in the database, so keeping them for the telemetry window would be a different decision than the one an operator makes by turning capture on. The REST surface (`GET /traces`, `GET /traces/{id}`) is `sessions:read`, **not** `eval:read`: a trace is turn content, and the eval scopes belong to a judge that must never resolve a live prompt. The list response repeats the capture switch so the inspector can tell "nothing recorded yet" from "recording is off"; a failed read renders neither empty state, or a 503 would read as a config problem. `CountTraces` takes the same `TraceFilter` as `ListTraces` and the handler echoes `eval.BoundTraceLimit(limit)` rather than the requested one — a total counted over the whole table beside a filtered page makes "load more" ask for rows that can never arrive, and a pager trusting a clamped limit skips rows. The trace payload's `History` is *preceding* context only: the turn's own message is the last wire message either way, and `traceHistory` drops it so the inspector does not print the prompt twice. The byte cap is hard: `truncateTracePayload` measures encoded bytes (JSON escaping can sextuple a control character), attaches the truncation note *before* the final measurement because the note rides inside the payload, and halves the text budget until it fits. **Dry-run traces are built but never stored** — a preview's trace rides out on its `TurnResult`, so `source=dryrun` is a value the column accepts and no row ever holds; the inspector offers no dry-run chip.
- **Audit marking travels in the context, not the policy**: `policy.mark()` builds an `agentctx.ExecMark` installed once per turn; `Engine.emitAudit` applies it. That single overlay is what makes marking *total* — a dozen emit sites, several in helpers that never see the policy, all get `source` = `dryrun`/`eval` and `agent` = `{name}#dryrun` / `{name}#eval:{variant}`. `#` is rejected by `ValidResourceName`, so exact-match `?agent=` queries exclude these for free. `AuditMode: "summary"` (`[eval] audit`) drops ok-status non-`eval` events only. The cost tracker also registers the pseudo-agent, so preview spend never lands in a real agent's totals.
- **`exclude_source` applies to list *and* stats**: dry-run/eval per-round events carry the *existing* `llm`/`tool_call` categories, so a category chip cannot separate them — source is the only discriminator. `audit.Store.Stats` therefore takes `StatsOpts` (not a bare `since`), and `Stats` reuses `buildWhereClause` so the exclusion can never drift from `List`; the events-last-hour window applies it too. The AuditLog page's "Previews → Show dry runs & evals" toggle passes `exclude_source=eval,dryrun` on **both** queries. It is a shared `.chip` inside a `.filter-chips` container paired with a `.filter-label`, **not** a bare button appended to `.filters` — that container is a `48px 1fr` grid of label/control pairs, so a direct child lands in the narrow label column and renders as a wrapped blob. The row is labelled "Previews" rather than "Evals" because `categoryItems` already carries an `Evals` entry for the `eval` lifecycle *category*, which filters a different axis.
- **Skill dry-runs pick an invocation, not always a message**: `mode` ∈ `schedule`/`command`/`message`, resolved by `resolveSkillMode` (explicit wins → a non-empty `message` keeps message semantics → `command:` trigger → a schedule naming the skill → else `message`). The modes differ in more than text: only `schedule` sets `msg.SkillName` (which is what forces body injection) and `IsScheduled`; `command` and `message` leave `SkillName` empty so ordinary trigger matching runs, so a command preview exercises the trigger rather than bypassing it. Before this, the handler set `SkillName` *and* used a typed message with `IsScheduled: false` — a hybrid matching neither real path, which is why a scheduled skill previewed that way wasn't testing what happens when it fires.
- **Ambient ≠ scheduled, and frontmatter cannot tell them apart** (#305): a triggerless skill matches *every* turn and reads the user's own text; it is scheduled only if `[[schedules]]` names it. The inference therefore consults `Scheduler.Entries()` (`Server.schedulesForSkill`, agent-scoped with the same empty-`Agent`→fallback resolution `handleDryRunSchedule` uses, sorted — `Entries()` walks a map), and a skill with neither trigger nor schedule defaults to `message`. When a schedule *does* fire it, the preview is built by `configmcp.BuildScheduledMessage` from that entry, so `ScheduleName`/`ScheduleCron`/tier match the real fire rather than being blank; the transcript echoes `scheduled_by`. Explicit `mode:"schedule"` on an unscheduled skill still works (a hypothetical) and keeps the synthesised header. `GET /skills` and `/skills/{agent}` carry `scheduled_by` (omitted when nothing schedules the skill) — that is the **only** signal `SkillInvocation.svelte` has to preselect the right chip.
- **`configmcp.BuildScheduledMessage` is shared by the live job closure and the schedule dry-run endpoint** — a preview is by construction the message the schedule fires (header, skill, cron), not a re-creation that can drift. Both dry-run endpoints sit behind their parent's **write** scope: they persist nothing but execute read tools and spend real tokens.
